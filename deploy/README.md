# Закрытый пилот Qodex

Для запуска нужны Linux-сервер с Docker Compose, DNS для выбранного имени и TCP-порты 80/443 до Caddy. Пилот использует отдельный пустой том, приложение доступно через HTTPS-прокси. Локальный Compose использует демоданные и тестовые учётные записи.

## Личный вход через HTTPS

Подготовьте файл пользователей вне репозитория. Это пример структуры, введите свои уникальные пароли.

```json
{
  "owner": {"role":"owner","password":"ЗАМЕНИТЕ"},
  "finance": {"role":"finance","password":"ЗАМЕНИТЕ"},
  "manager": {"role":"manager","password":"ЗАМЕНИТЕ","projects":["Ро-бот"]},
  "employee": {"role":"employee","password":"ЗАМЕНИТЕ"}
}
```

На сервере сделайте файл доступным для чтения UID 65534 внутри контейнера и закройте доступ остальным пользователям. Для прямого bind mount на Linux используйте владельца 65534 и права 0400, либо эквивалентное разрешение для пользователя контейнера. Укажите `QODEX_DOMAIN` и абсолютный путь `QODEX_USERS_PATH` в закрытом файле окружения вне репозитория, затем запустите в папке проекта:

```bash
docker compose --env-file /secure/qodex.env -p qodex-pilot -f compose.pilot.yaml up --build -d
```

Файл добавляет новые учётные записи при запуске. Изменённые роли, пароли и отключённые записи хранятся в базе и не перезаписываются исходным файлом. Для существующего стенда без владельца добавьте в файл новый логин с ролью `owner` и перезапустите приложение. Владелец управляет пользователями через раздел «Сотрудники».

Сотрудник подаёт заявки и видит свои. Руководитель видит финансовые данные и заявки назначенных проектов, планирует поступления и выплаты. Финансовый директор и владелец согласовывают или отклоняют заявки. Свою заявку согласует другой пользователь. Комментарии, PDF до 1 МБ и уведомления доступны участникам с правом просмотра заявки.

## Корпоративный OIDC

Подключите приложение у корпоративного IdP с callback `https://<домен>/oauth2/callback`. Запишите в приватный файл окружения `QODEX_OIDC_ISSUER`, `QODEX_OIDC_CLIENT_ID`, `QODEX_OIDC_CLIENT_SECRET`, `QODEX_EMAIL_DOMAIN`, `QODEX_OIDC_COOKIE_SECRET` и `QODEX_PROXY_TOKEN`. Секрет Cookie можно создать через `openssl rand -base64 32`, общий токен приложения и прокси через `openssl rand -hex 32`. Ключи JSON пользователей должны совпадать с адресами из IdP. В режиме OIDC пароли в JSON не требуются, MFA задаётся политикой IdP.

```bash
docker compose --env-file /secure/qodex.env -p qodex-pilot -f compose.pilot.yaml -f compose.sso.yaml up --build -d
```

Приложение и OAuth2 Proxy остаются во внутренней сети Compose. Caddy проверяет пользовательскую сессию перед передачей идентификатора. Для рабочего запуска проверьте вход с реальными ролями, отказ для адреса вне списка и выход через корпоративный IdP.

## Резервная копия и восстановление

Работающая SQLite копируется через штатный SQLite Backup API. Используйте новое имя файла для каждого запуска. Для локального Compose:

```bash
docker compose -p qodex-main exec -T qodex python /app/db_admin.py backup /tmp/qodex-backup.sqlite3
docker compose -p qodex-main cp qodex:/tmp/qodex-backup.sqlite3 ./qodex-backup.sqlite3
docker compose -p qodex-main exec -T qodex rm /tmp/qodex-backup.sqlite3
```

Для онлайн-пилота укажите те же имя проекта, файлы Compose и файл окружения, что при запуске. Резервная копия содержит финансовые данные и PDF. Храните её вместе с отдельно защищённой копией настроек пользователей и окружения.

Для учебного восстановления используйте отдельный проект `qodex-recovery` с новым томом. Следующие команды загружают выбранную копию без запуска веб-сервера.

```bash
docker compose -p qodex-recovery run --rm -d --no-deps --name qodex-recovery-loader qodex sleep 600
docker cp ./qodex-backup.sqlite3 qodex-recovery-loader:/tmp/input.sqlite3
docker exec -u 0 qodex-recovery-loader chown 65534:65534 /tmp/input.sqlite3
docker exec -u 0 qodex-recovery-loader chmod 0400 /tmp/input.sqlite3
docker exec qodex-recovery-loader python /app/db_admin.py restore /tmp/input.sqlite3
docker stop qodex-recovery-loader
```

Команда восстановления проверяет целостность и отказывается перезаписывать существующую базу. Запустите проект на отдельном порту, сравните банк, начисления, открытые заявки и журнал с исходной базой. Периодичность резервирования и срок хранения выбираются владельцем учёта.

## Проверочный регламент месяца

Финансист сверяет счета, завершает разнесение, проверяет ожидаемые документы и подтверждает строки графиков. Закрытие фиксируется по ООО, основание и замечания попадают в журнал. Закрытые месячные операции, начисления, распределения и первичный план защищены от правок. Новые или изменённые банковские движения до закрытой даты также блокируются, поскольку они могут поменять входящий остаток. Для исправления откройте нужный период с причиной. Шаблон представления P&L применяется актуальный.
